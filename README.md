# iProxypac

`proxy.pac` を安全に管理・生成・テストするための単一HTMLツールです。すべての機能が `iProxypac.html` 1ファイルに収まっており、外部API・CDN・外部ライブラリには依存しません。閉域環境にファイルを1つコピーするだけで利用できます。

現在のバージョン: **v0.1.3**

### v0.1.3での変更点（不具合修正・整理）

- **「アクセス経路」タブでの設定変更が画面に反映されない不具合を修正しました。** 既定経路・`isPlainHostName` 共通ルールの有効/無効・その経路をプルダウンやチェックボックスで変更しても、「PAC」タブには変更前の古いPACが表示されたままになり、「設定が変更されています」の警告も出ませんでした。さらにこの状態では「proxy.pac をダウンロード」を押しても何も起きませんでした。設定変更時は必ず全タブを再描画するよう、保存処理に一本化しています。
- **PACが生成されていない状態で「コピー」「proxy.pac をダウンロード」を押しても無反応だった点を修正しました。** 「検証してPACを生成」を実行するよう促すメッセージを表示します。またコピーは画面上の文字列ではなく、生成済みPACそのものを対象にしました。
- **条件の種類が不明なデータを読み込むと、PAC生成ボタンが無反応になる不具合を修正しました。** （このツールが対応していない条件の種類を含むJSONを読み込んだ場合など。）入力検証で「条件の種類が不明です」というエラーとして表示します。
- **同一システム内で同じ条件を2回登録したとき、「自分自身と重複しています」という意味の通らない警告が二重に出ていたのを修正しました。** 同一システム内の重複は1件の警告にまとめ、他システムとの重複のみ別途警告します。
- **回帰テストを実行しても、テストURLが1件も無いシステムの一覧表示が「未実行」のままだった点を修正しました。** 「テストURLなし」「対象外（無効）」と表示を分け、再実行しても変わらない状態が分かるようにしました。
- **アクセス経路の「使用箇所」の件数が実態より多く数えられていた点を修正しました。** 同じシステムのテストURLを複数件数えていたためです。あわせて、削除できない理由の一覧にガードテストのURL・テストURLの件数を表示し、どこを直せばよいか分かるようにしました。
- ブラウザへの自動保存に失敗した場合、これまでは何も表示されませんでしたが、JSON書き出しでのバックアップを促すメッセージを表示するようにしました。
- 内部実装を整理しました（未使用の変数・到達しないコードの削除、回帰テスト実行処理の共通化、条件抽出処理の共通化、テストURL行の削除処理を条件行と同じ方式へ統一）。データ構造・JSON `formatVersion`・PAC生成結果・優先順位の扱いは変更していないため、既存のJSONバックアップはそのまま読み込め、同じ設定からは従来と同じ `proxy.pac` が生成されます。

### v0.1.2での変更点

- システム追加・編集画面を「この条件に一致したら、この接続方法を使う」という1つのルールとして理解できるUIへ再構成しました。「このシステムと判定する条件」と「接続方法」を1つの枠内にまとめ、矢印と「この条件に一致したら」という文字で両者のつながりを示しています。
- 条件の種類は「ホスト名が完全一致」「ワイルドカードで一致」「ドメイン配下に一致」「IPアドレスが完全一致」という意味の分かる名称で選択できるようにしました。`shExpMatch()` などのPAC関数名は、選んだ条件の下に補足として表示されるだけで、前面には出しません。条件の種類を切り替えると入力欄のplaceholderと補足説明が連動して切り替わります。
- 「接続方法」の選択肢にはアクセス経路の表示名（例: 国システム用プロキシ）を表示し、選択後にPAC上の実際の値（`PROXY 192.0.2.10:8080` など）を補足表示します。`DIRECT` を選んだ場合は「プロキシを経由せず直接接続します。」という説明を表示します。
- 「この設定の意味」として、入力中の条件と接続方法から自然文のプレビュー（例: 「service.example.go.jp に一致した場合、プロキシを経由せず直接接続します。」）をダイアログ内に即時表示するようにしました。
- `DIRECT` と国ドメイン等の組み合わせのような、意味的にありうる設定を機械的に禁止することはしていません（入力検証の対象は従来どおり、名称未入力・値未入力・不正なIP・経路の競合などに限られます）。
- 既存データ構造・JSON `formatVersion`・PAC生成ロジック・優先順位・URL単体テスト・回帰テスト・ガードテスト・v0.1.1の生成PAC鮮度管理（設定変更時の無効化）はいずれも変更していません。既存のJSONバックアップはそのまま読み込めます。

### v0.1.1での変更点

- 設定（システム・アクセス経路・ガードテスト・優先順位など）を1箇所でも変更すると、既に生成済みのPAC・構文検証結果・回帰テスト結果を自動的に無効化するようにしました。変更前の古い `proxy.pac` を誤ってダウンロードできてしまう問題を修正しています。「PAC」タブには「設定が変更されています。PACを再生成してください」という警告が表示され、再生成するまでプレビュー・ダウンロードは表示されません。
- 「サンプルデータを削除」は、サンプルとして投入したシステム・ガードテスト・アクセス経路のみを削除するようにしました。利用者が追加したデータは削除されません。サンプルのアクセス経路であっても、利用者が追加したシステム等から実際に参照されている場合は残します。
- 生成したPACのコメントに埋め込むシステム名から、改行等を除去して安全化しました。
- `shExpMatch` のテスト実行時の変換ロジックを、Chromiumが提供するPAC標準ライブラリの実装（`.`/`*`/`?` のみを変換）に合わせました。
- アクセス経路の値に `HTTPS` / `SOCKS4` キーワードも指定できるようにしました（Chromiumが対応する経路キーワードに準拠）。

## 目的

閉域環境から国提供システム等のパブリックサイトへアクセスするために `proxy.pac` を運用していると、次のような課題が発生しがちです。

- PACを手書きすることによる構文ミス
- 新しいルールを追加した際の、既存システムへの巻き添え（意図しないルールの上書き・シャドーイング）
- どのURLがどのルールに該当しているのかが分かりにくい
- PACを安全にデバッグできる環境がない

iProxypac は、対象システムを**構造化データ（システム台帳）として管理**し、その情報から `proxy.pac` を**自動生成**し、**URL単体テスト**と**全件回帰テスト**を行えるようにすることで、これらの課題に対応します。

## 主な機能

- **システム管理**: システム名・備考・優先順位・接続方法・このシステムと判定する条件（複数）・回帰テストURL（複数）・有効/無効を一覧管理
- **判定条件**: 「ホスト名が完全一致」「ワイルドカードで一致」「ドメイン配下に一致」「IPアドレスが完全一致」という意味の分かる名称で選択（内部的には host完全一致 / `shExpMatch` / `dnsDomainIs` / IPアドレス完全一致に対応）。`isPlainHostName` は共通ルールとして別枠で管理
- **アクセス経路管理**: `DIRECT` / `PROXY host:port` などをマスターとして一元管理し、システム側では選択するだけ
- **優先順位管理**: 一覧から並び替え可能。PAC生成時も必ずこの順序を使用（先に一致した条件が優先）
- **PAC自動生成**: 人間が読みやすい整形済みコードを生成。同じ設定からは常に同じPACが生成される
- **入力検証**: システム名未入力、条件未入力、不正なIP、不正なポート、重複条件、経路の競合、無効な経路参照などをエラー/警告に分けて検出
- **PAC構文検証**: 生成したコードを実際に `Function` として構築し、`FindProxyForURL` が定義できること・構文エラーがないことを確認
- **URL単体テスト**: Chromium系ブラウザがPACへ渡すURL（path/queryが除去される挙動）を模したうえで、生成PACを実際に実行して判定結果を表示
- **全件回帰テスト**: 各システムの登録済みテストURLと、システムに属さない「ガードテスト（対象外URLがDIRECTのままであることの確認等）」をまとめて実行し、PASS/FAILを集計
- **重複・競合検出**: 完全一致条件の重複、異なる経路への割り当て、広いワイルドカードによる狭い条件のシャドーイングなどをヒューリスティックに警告
- **JSON保存・復元**: すべての設定をJSONとしてエクスポート/インポート可能（`formatVersion` により将来の互換性に配慮）。ブラウザの `localStorage` による自動保存も行われますが、正式なバックアップ手段は必ずJSON出力を使用してください
- **proxy.pac出力**: 検証済みのPACをファイルとしてダウンロード

## 前提・制約（重要）

- **想定ブラウザ**: Microsoft Edge / Google Chrome などの Chromium系ブラウザです。PACへ渡されるURLがpath/queryを除去される挙動を前提にテストエンジンを実装しています。Firefox固有の挙動には対応していません。
- **実通信テストではありません**: 本ツールは実際のWebサイトへの接続確認やプロキシ経由の通信テストは一切行いません。あくまで `FindProxyForURL()` の**論理的な判定結果**を検証するものです。
- **DNS依存判定には制約があります**: DNS問い合わせ・名前解決は行いません。IPアドレス条件は「URLのhost自体がIPアドレスである場合の完全一致」のみをサポートし、ホスト名からIPアドレスを引く処理（逆引き含む）は行いません。
- その他、v0.1.0で扱わない範囲は本書末尾の「既知の制約・v0.1.0のスコープ外」を参照してください。

## 基本的な利用手順

1. **アクセス経路を登録する**（「アクセス経路」タブ）
   `DIRECT` や `PROXY 192.0.2.10:8080` など、実際にPACが返す値をマスターとして登録します。ここで付けた「表示名」（例: 国システム用プロキシ）が、システム登録画面では「接続方法」の選択肢として表示されます。既定経路（最終的にどの条件にも一致しなかった場合の経路）もここで設定します。
2. **システムを登録する**（「システム」タブ）
   「+ システム追加」を開くと、以下の流れで1つのシステムを登録できます。
   1. システム名を登録する
   2. このシステムと判定する条件を登録する（「ホスト名が完全一致」「ワイルドカードで一致」など、意味の分かる名称から選択し、値を入力します。PAC関数名を知らなくても設定できます）
   3. 条件に一致した場合の接続方法を選択する（選んだ経路の実際のPAC値や、`DIRECT` の意味がその場で表示されます）
   4. 必要に応じて回帰テストURLを登録する
   ダイアログ内には「この設定の意味」として、登録内容を自然文でまとめたプレビューが表示され、条件や接続方法を変更すると即座に更新されます。
3. **URL単体テストを行う**（「テスト」タブ）
   実際に判定したいURLを入力し「判定」を押すと、PAC評価用URL・host・判定結果・該当システム・該当条件が表示されます。
4. **全件回帰テストを行う**
   「全件回帰テスト実行」で、登録済みの全テストURLと共通（ガード）テストをまとめて実行し、PASS/FAILを確認します。
5. **PACを生成する**（「PAC」タブ）
   「検証してPACを生成」を押すと、入力検証・PAC構文検証・回帰テストが一括で行われ、生成されたコードがプレビューされます。エラーがある場合は生成されません。
6. **`proxy.pac` を出力する**
   内容を確認のうえ「proxy.pac をダウンロード」でファイルを出力します。回帰テストにFAILが残っている場合は警告が表示されますが、出力自体は可能です。本番投入前に必ず内容を確認してください。

設定内容は「JSON書き出し」でいつでもバックアップでき、「JSON読み込み」で復元できます。

## 初期サンプルデータについて

初回起動時には、機能を把握しやすいよう架空のサンプルシステム・アクセス経路・ガードテストが投入されています。実在のシステム名やIPアドレスは含まれておらず、IPアドレスは例示用として予約されたアドレス帯（192.0.2.0/24 等、RFC 5737）を使用しています。不要になった場合は「システム」タブに表示されるバナーから一括削除できます。

## 既知の制約・v0.1.0のスコープ外

以下はv0.1.0では意図的に実装していません。

- 実際のWebサイトへの接続確認、実際のプロキシ経由通信テスト
- DNS問い合わせ、ホスト名からIPアドレスを取得する処理（逆引き・正引きとも）
- Firefox固有のPAC挙動への対応
- PACの完全なステップデバッガ
- 任意の既存PAC JavaScriptをGUIへ逆変換する機能
- PAC JavaScriptを自由編集する高機能コードエディタ
- 外部ライブラリの導入

これらは将来のバージョンで必要に応じて検討します。
